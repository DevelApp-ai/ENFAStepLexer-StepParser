# Issue #101 measurement harness — incremental-parsing-ides article

Supports `articles/incremental-parsing-ides/content/main.md`
(measurement backlog tracked in DevelApp-ai/ENFAStepLexer-StepParser#101).

## What is measured

**Committed corpus + traces + scripts** (acceptance criterion):

- `src/DevelApp.Benchmarks/Corpus/issue-101/cs-{100,500,2000,5000}.txt` —
  deterministic C#-like source files at 100/500/2000/5000 lines, generated by
  the committed `gen_corpus.py` (seeded; verified to lex cleanly against the
  real CSharp10 grammar).
- `src/DevelApp.Benchmarks/Corpus/issue-101/traces/{char-insert,word-completion,line-insert,block-paste}.json` —
  40 deterministic edits each (the article's four edit types).

**Harness**: `Issue101Measurement` (`--measure-issue101 <outDir>`) runs every
(size, trace) under two configurations with the CSharp10 grammar from
Minotaur-Grammars@main:

- `full-relex` — per edit a fresh `RealTimeParserSession.Initialize` (full
  document re-lex; the lex-level cost of a from-scratch re-parse),
- `incremental` — one session, per-edit `ApplyEdit` (the windowed re-lex +
  tail-token reuse from issue #144; this engine's analogue of the article's
  Selective Path Invalidation).

Reported: per-edit latency medians (reps: full 3, incremental 10), p50/p95
across each trace, token-reuse ratio per edit type
(`LastReuseRatio`), cold-start ratio (mean of first 20 edits / mean of rest),
allocation per edit, a log-log latency-vs-size fit (tests the "approximately
O(log n)" claim), and a parse-time table (`Parse()` per size; skipped above
2000 lines in CI to bound GLR memory). Outputs: `issue-101-edit-latency.csv`,
`issue-101-summary.json`, `RESULTS.md`.

`SessionEditLatencyBenchmarks` (BenchmarkDotNet) provides the same
full-relex-vs-incremental comparison as a Ratio-column benchmark
(`--filter '*SessionEditLatencyBenchmarks*'`).

## Not measured here (external baseline)

- The tree-sitter column of the article's comparison table: no tree-sitter
  binding exists on the .NET CI runner. Run the same traces against
  tree-sitter's C# grammar on a machine that has it and append the column.
- Recorded IDE sessions: the traces are scripted and deterministic; if real
  IDE recordings become available, drop them into `traces/` as JSON in the
  same format.

## How to run

```bash
dotnet run -c Release --project src/DevelApp.Benchmarks -- --measure-issue101 out/issue-101
dotnet run -c Release --project src/DevelApp.Benchmarks -- --filter '*SessionEditLatencyBenchmarks*' -j short
```

## CI

The `article-measurements` job in `.github/workflows/ci.yml` runs the
measurement on every PR/push and uploads the `article-measurements` artifact;
measured values are transcribed into `RESULTS.md` next to this README.
